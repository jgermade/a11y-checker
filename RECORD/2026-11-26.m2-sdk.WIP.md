## 2026-11-26 — Implementation

**`@a11y-checker/sdk`:**

- API:
  - `check(options?)` and `createChecker(options?)`, where options are a `CheckConfig`
    plus `engines` and `document`. The default engine is axe-core.
  - `createChecker` validates the config when it is created.
  - `checker.check(overrides)` merges `overrides` over the base config with
    `mergeConfig`: `wcag` and `rules` are merged key by key, everything else is replaced.
  - The SDK re-exports the core types and `createAxeEngine`.
- Builds (tsdown, two configs):
  - ESM + CJS with `.d.ts`/`.d.cts`. Entries are `.` and `./reporters`; the second loads
    no engine.
  - IIFE `dist/a11y-checker.iife.js` (683 kB minified, 194 kB gzip, axe-core included),
    global `A11yChecker`, exported as `@a11y-checker/sdk/iife`.
  - The build script empties `dist/` itself, because the two configs run in parallel.
- Reporters:
  - `toJSON`.
  - `toSARIF` (SARIF 2.1.0): one SARIF result per node. Violations with critical or
    serious impact have level `error`; other violations have level `warning`;
    incomplete results have kind `review`. The URL is the artifact location, the
    formatted selector is the logical location, and the HTML is the snippet. Rules are
    tagged `WCAG x.y.z` and `ACT id`. Engine errors set `executionSuccessful: false`.
  - `toHTML`: a standalone, accessible page with light and dark mode and no external
    resources. Everything is escaped, and only `http(s)` links are rendered.
- `formatTarget()` was added to core: `iframe#app → #host >>> button`.

**Finding — cross-origin iframes:** axe-core only talks to same-origin frames by default,
and it **skips cross-origin frames silently**: no error and no incomplete result. Added
`allowFrameOrigins(origins)`, plus the `SAME_ORIGIN` and `ALL_ORIGINS` constants, to
engine-axe, the SDK and the IIFE. Both sides must allow each other's origin. The default
stays same-origin only, because results carry HTML from the frame.
→ Follow-up for M3: the extension should configure the origins per frame, and warn
about frames it could not check.

**Tests (80 in total):**

- SDK API in happy-dom.
- Reporters: SARIF structure, HTML escaping and XSS, JSON round trip.
- Built IIFE in Chromium through Playwright, in a Node environment. The test builds
  first.
  - API surface and injection with `addScriptTag`.
  - Cross-origin iframe: skipped by default, checked once origins are allowed.
  - **The HTML report checks itself with no violations in light and dark mode** (WCAG
    2.2 AA + best practices, all `<details>` expanded).
- Packaging checked manually:
  - `pnpm pack` replaces `workspace:^` with real versions and includes the root
    LICENSE.
  - Installing the tarballs works in Node ESM, CJS, the reporters subpath, the IIFE
    resolution and jsdom.
  - TypeScript resolves the types with `NodeNext` and `skipLibCheck: false`.

**Release:**

- `.changeset/initial-release.md` bumps core, engine-axe and sdk as `minor`, to 0.1.0.
- `.github/workflows/release.yml` uses changesets/action on `main` with npm provenance.
  It needs an `NPM_TOKEN` secret.

**Deviation from the plan:** `check(target?, options?)` became `check(options?)`.
Element-level targets (for example, component tests) are deferred to P2. The config
stays JSON-serializable, which the extension needs for messaging.

**Pending to close M2:** the first npm publish. It requires the project owner to add the
`NPM_TOKEN` secret and merge the branch into `main`.

## 2026-11-26 — `make publish`

Added a root `Makefile` as a manual alternative to the release workflow:

- `make publish` refuses to run with a dirty tree, outside `main` (override with
  `PUBLISH_BRANCH=...`) or without `npm whoami`. It applies pending changesets
  (`pnpm version-packages`), refreshes the lockfile, commits "Version packages", runs
  `make check` (format, lint, typecheck, build, tests) and `pnpm changeset publish`.
  It does not push; it prints `git push --follow-tags` instead.
- `make publish-dry-run` builds and runs `pnpm -r publish --dry-run`.
- Local publishes carry no npm provenance; the CI workflow is still preferred.
- `make check` mirrors CI, except for the Cypress-required flag and the extension zip.

## 2026-11-26 — Build fix for Node without native TypeScript

`make publish` failed on the owner's machine: tsdown 0.23 loads `tsdown.config.ts`
natively only when `process.features.typescript` is set (Node ≥ 22.18). Otherwise it
falls back to the optional peer `unrun`, which was not installed. Added `unrun` as a root
devDependency. Verified by building `packages/core` with `--no-experimental-strip-types`.

## 2026-11-26 — Minimum Node version raised to 22.19

The next `make publish` attempt on the owner's machine failed in
`packages/engine-axe/test/jsdom.test.ts`: jsdom 31 depends on undici 8, which requires
Node ≥ 22.19 (it calls `zlib.createZstdDecompress` at import time). The `unrun` fix was a
symptom of the same old Node. Changes:

- Root `engines.node` is now `>=22.19` (development only; published packages keep their
  own `engines`).
- `scripts/check-node-version.mjs` reads that minimum and fails with a clear message.
  `make install` (and therefore `check` and `publish-dry-run`) and `make publish` run it
  first. `make node-version` runs it on its own.

## 2026-11-27 — Manual release workflow with a bump input

Owner's decision: `release.yml` is run by hand with the version bump as input
(`patch` / `minor` / `major`), and it calls `build.yml` to test and build before
publishing (the owner's usual `build.yml` + `release.yml` layout).

- `ci.yml` was renamed to `build.yml`. It still runs on every push, and also accepts
  `workflow_call` with an optional `ref`. It uploads `packages/*/dist/` as the
  `packages-dist` artifact. Its concurrency group includes `github.workflow`, so a release
  build and a push build never cancel each other.
- `release.yml` (workflow_dispatch, `main` only) has three jobs:
  1. `version`: `scripts/prepare-release.mjs <bump>` rewrites every pending changeset to
     the chosen bump (or creates one for all public packages when none are pending),
     then `changeset version`. Commits "Release vX.Y.Z" and force-pushes it to the
     temporary branch `release-candidate`.
  2. `build`: calls `build.yml` on that commit. Building after the bump is required:
     sdk, cli and engine-native bundle `package.json` (and so their version) into `dist`.
  3. `publish` (environment `production`, OIDC): fast-forwards `main` to the release
     commit (fails before publishing if `main` moved), downloads `packages-dist`, runs
     `changeset publish` and pushes the tags. Re-running it after a partial failure is
     safe.
- `.changeset/config.json` has `fixed: [["@a11y-checker/*"]]`: one shared version.
- The changesets/action PR flow is gone, so the "Allow GitHub Actions to create pull
  requests" setting is no longer needed. The `changeset-release/main` branch left by the
  failed run can be deleted.
- `make publish` now requires `BUMP=patch|minor|major` and uses the same script.

Verified in a scratch worktree: with the five pending changesets and `patch`, every
package went from 0.0.0 to 0.0.1 and the changelogs kept the summaries; with none
pending and `minor`, the generated changeset bumped every package (extension included)
to 0.1.0. Workflow YAML parses; not run on GitHub yet. If `main` is protected against
direct pushes, the `publish` job needs a bypass for GitHub Actions.

## 2026-11-27 — First releases, missing tags and the stray 0.1.0

- The manual Release workflow published 0.0.1 and 0.0.2 of all nine public packages
  with OIDC (runs 45926518280 and 45927373380). `main` has the "Release v0.0.1" and
  "Release v0.0.2" commits.
- **No git tags were pushed.** Changesets creates annotated tags (`git tag X -m X`),
  which need a git identity; the `publish` job had none, so `git tag` failed silently
  and `git push --tags` found nothing. Fix: the `publish` job now configures the
  github-actions[bot] identity first. Reproduced locally (exit 128 without identity).
  Tags for 0.0.1 and 0.0.2 are still missing.
- **0.1.0 is on npm** for every public package (published 01:39 UTC by the owner's local
  `make publish`, from the old changesets). `latest` is 0.0.2. A future `minor` from
  0.0.x would compute 0.1.0, and `changeset publish` would silently skip it. Fix: the
  `version` job now fails if any public package already has the new version on npm.
  Checked against the registry: 0.1.0 clashes for all nine packages, 0.0.3 for none.
- Open for the owner: deprecate 0.1.0 on npm, and decide how to get past it on the
  first minor release.
