# M1 — Core engine + axe-core provider

Plan: `ROADMAP/2026-11-26/mvp.md#m1--core-engine--axe-core-provider`.

## 2026-11-26 — Implementation

**`@a11y-checker/core`:**

- Result model (`types.ts`): `Issue`, `IssueNode`, `NodeTarget`, `Impact`, `Outcome`,
  `CheckSummary`, `EngineInfo` and `EngineError`.
  - `Issue.id` is `<engine>/<ruleId>/<outcome>`.
  - `NodeTarget` is `string[][]`: one entry per frame level, and within each level the chain
    of selectors through shadow roots. This is the same structure axe uses, normalized to
    always use arrays.
- Config (`config.ts`): `CheckConfig`, plus `resolveConfig()` with runtime validation
  (`ConfigError`) and no dependencies. The defaults are WCAG 2.2 AA, outcomes
  violation + incomplete, and no best practices.
- `EngineProvider` (`engine.ts`): `{ id, version, run(context, config): Promise<Issue[]> }`.
- Runner (`runner.ts`): `runCheck({ engines, document?, config? })`.
  - Engines run sequentially; an engine that throws is reported in `errors`.
  - The runner applies the scope filter (`isIssueInScope`) to every engine's output, so all
    engines behave the same way even if they ignore part of the config.
  - Issues are sorted by outcome, then impact, then rule, then engine.
- WCAG data (`wcag.ts`): all 87 WCAG 2.x success criteria (61 + 17 + 9), with level, the
  version that introduced them, and `4.1.1` marked as removed in 2.2.
  `isCriterionInScope(id, version, level)`.

**`@a11y-checker/engine-axe`** (axe-core 4.14.1):

- `createAxeEngine({ axe? })`.
- The WCAG target becomes axe tags, intersected with the tags axe knows. Rule
  include/exclude lists become `runOnly` and `rules`; IDs axe does not know are dropped,
  because they may belong to another engine. Selectors become the axe context.
- WCAG mapping is parsed from axe tags (`wcag1410` → `1.4.10`). ACT IDs come from
  `axe.getRules()[].actIds`, which axe has exposed since 4.x. **No hand-maintained
  mapping table is needed for axe.**
- Calls are queued per axe instance, because axe throws when two runs overlap.
- The bundled axe only checks the global document. For other windows (jsdom), the caller
  passes that window's axe instance.

**Tests (57):**

- Core unit tests: config, WCAG scope, filtering, sorting, runner behavior.
- axe unit tests: normalization and option building.
- Integration in **happy-dom**: axe-core works there. It detects DOM-only rules
  (image-alt, button-name); contrast is left as incomplete.
- Integration in **jsdom** (Node environment) through an injected axe instance.
- Integration in **Chromium**: basic fixture, WCAG level filtering (A / AA / AAA),
  rule and selector filters, passes, shadow DOM, same-origin iframe (axe injected into
  the frame), dynamic content, and concurrent calls.

**Decisions and deviations from the plan:**

- The plan described the provider interface as `run()` + `normalize()`. It ended up as a
  single `run()` that returns normalized issues; `normalizeResults()` is still exported
  from engine-axe for tests. This keeps the interface minimal for the IBM provider and the
  in-house engine.
- `tsconfig.base.json` `paths` and a Vitest alias resolve `@a11y-checker/*` to package
  sources, so typecheck and tests do not need a build first. tsdown treats workspace
  dependencies as external.
- ESLint allows numbers in template literals (`restrict-template-expressions`).
- Finding: axe's `color-contrast-enhanced` (AAA) does not report nodes that already fail
  `color-contrast` (AA).

**Not covered yet (follow-ups):**

- Cross-origin iframes. They need axe injected in every frame, which is the extension's
  job in M3 (`all_frames`).
- Cross-engine dedup. This is planned for P1; the ACT/WCAG fields it needs are already
  populated.
- The injectable IIFE bundle. It is planned for M2 (SDK).
